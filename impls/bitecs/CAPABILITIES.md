# Capabilities: bitecs

Library version: bitecs 0.4.0 (npm release, `latest`)

Each row names a need of the game. The `Support` column says how bitecs meets it, and the `Code` column links the code that uses the library API. The three `Support` values are `native` (the API does the job as its docs teach), `emulated` (built from other features or a manual pass) and `absent` (the library has no way, so the implementation does something else). A note on a `native` row means a workaround from [Notes](#notes) is part of it.

## Notes

- **Spatial index.** The kernel owns the grid. bitecs keeps it current with calls: `add` at spawn ([spawning.ts L77](src/spawning.ts#L77)), `update` for each unit that `move` sets ([move.ts L58](src/systems/move.ts#L58)), `remove` and `add` when a unit enters or leaves a garrison ([garrison.ts L8-L19](src/garrison.ts#L8-L19)), and `remove` from the `onRemove(Unit)` observer, which also catches the minions that the cascade of `destroyEntity` removes ([context.ts L64](src/context.ts#L64)). The `inGrid` array stops the observer from removing a garrisoned unit twice. The handle is the entity id, so `Team.value[handle]` replaces a map back from the handle.
- **Start-of-phase positions.** SoA stores are not double-buffered. The `Start` component copies `Position` in the `moveStart` step, which the runner calls right before `move` ([move.ts L8](src/systems/move.ts#L8)). The deep-dive report shows it as its own `move.start` line.
- **Why not relations.** bitecs 0.4 relations were the first version of this implementation, and `war` took 15 to 20 minutes for one seed. Measured on `battle` (400 ticks, one process): 11.8 s with relations and 1.9 s without. 57% of the first profile was `removeEntity`. A pair `Rel(target)` registers a component for each target entity that is ever used. Destroying a target registers a `Wildcard(target)` query, which scans every live entity once and then stays in the world. `removeEntity` loops over all registered queries, and `addComponent` and `removeComponent` loop over the generations of component masks, so each destroy costs more for every id that was ever a target. Subjects pay too. `addComponent` of a pair puts both the subject and the target in `ctx.entitiesWithRelations` (bitecs `dist/core/index.mjs` L913-L917), and `removeEntity` builds a fresh `query(world, [Wildcard(eid)])` for each such entity (L1006), which scans all live entities and stays in `ctx.queries`. `removeRelation` never prunes the set. So a unit with any native link costs a full scan when it dies. `getRelationTargets` also copies the component list of the entity on each call. The docs show relations for small graphs. This game has about 50k entities, a destroy burst of hundreds each tick and a link in nearly every unit. So every link is a plain SoA component that stores the target entity id, as the bitecs docs teach for data that is not a flag. The cost is that bitecs no longer clears the link when the target dies, so the game does it (workaround 1). `GarrisonOf` is the one link that could be native, since its fan-in is small and bounded by `garrisonCap`. It stays emulated because a pair would still put every shrine and every unit that ever garrisons into `entitiesWithRelations`, so each of their destroys would scan all entities, and the link would need a read path unlike the other five. This is argued from the bitecs source and not measured on `war`.
- **Workaround 1, clearing links by hand.** A destroyed entity cannot clear the plain stores that name it, and bitecs recycles ids at once. `destroyEntity` is the one destroy function ([spawning.ts L32](src/spawning.ts#L32)): it destroys the minions of the entity, removes the entity from the reverse lists of its own links, destroys the items it holds, and records a destroyed unit in `ctx.destroyed`. `sweepDestroyed` ([spawning.ts L48](src/spawning.ts#L48)) then walks `query(world, [GameId])` once and clears `Targets`, `LastHitBy` and `FiredBy` that name a destroyed unit and the threats from it. It runs inside `cleanup` ([cleanup.ts L80](src/systems/cleanup.ts#L80)), before the projectile check reads `Targets.to` and before any spawn can reuse an id. Nothing else destroys units. Inside the destroy loop a link can name an entity that was just removed, so the kill credit checks `entityExists`.
- **Workaround 2, reverse lists.** `MemberOf`, `ChildOf` and `GarrisonOf` keep `from[target]`, an array of subjects, because three reads need "who points at X": promotion of members, the minion cascade and count, and the garrison of a shrine ([relations.ts L4-L20](src/relations.ts#L4-L20)). `setLink` and `clearLink` keep it in step. The lists are short (members, minions, at most `garrisonCap`). `Targets` has no list, since its fan-in is large and only the sweep reads it. The stores are module-level, so `createContext` and `load` empty the lists with `resetStores`.
- **Workaround 3, items die with the unit.** `Equips` is a pair of arrays in the unit, and `destroyEntity` removes each item entity of a destroyed unit ([spawning.ts L44](src/spawning.ts#L44)).
- **Workaround 4, hierarchy order.** `Hierarchy(relation)` in a query orders entities by depth, but it needs a bitecs relation, and it registers one query for each parent entity to track depth. The game has two links (`MemberOf` and `ChildOf`) and thousands of parents, so `move` computes the depth through the `to` arrays, memoized for the phase, and buckets the movers by depth ([move.ts L12-L33](src/systems/move.ts#L12-L33)).
- **Query cost.** The world holds a fixed set of queries, one for each term list in [queries.ts L7](src/queries.ts#L7) and the few inline term lists. Each `query` call hashes its terms, so a term list is a constant built once, and no system builds a query for each entity. The hot loops read typed arrays and never call `getRelationTargets`.
- **Per-entity arrays.** `Equips`, `Threat` and the reverse lists are plain arrays that are indexed by the entity id, and they are created for the entities that need them. A recycled slot is emptied by `newEntity` ([spawning.ts L13](src/spawning.ts#L13)), and a store is never cleared otherwise, so each write sets the whole value.
- **Component stores are module-level.** One process can hold two sims one after the other, and a store keeps the data of the first. Every spawn writes every field, and `load` rewrites them from the save.
- **Entity id capacity.** The stores hold `CAP = 131072` ids, and `newEntity` throws above it ([spawning.ts L13-L15](src/spawning.ts#L13-L15)). A typed array drops a write above its length without an error. The peak of `war` is about 50k entities.
- **Live query results.** `query` returns the live list of the query, and a removal is applied at the next committing `query`. No loop adds, removes or destroys while it reads a query result. Where a loop must change entities, it collects them first or copies the result with `Array.from`.
- **Recycled ids in the observer lists.** The lists that the `Added` observers fill can hold an entity that was destroyed before the phase read the list, and bitecs may have reused its id. The readers check `entityExists` and the tag again ([morale.ts L34](src/systems/morale.ts#L34), [stats.ts L33](src/systems/stats.ts#L33)).
- **Four questions from the guide.** Exclusive swap: `setLink` overwrites `to[subject]` and moves the subject between reverse lists. Cleanup on destroy: `destroyEntity` and `sweepDestroyed` clear what names the entity (workaround 1). Store lifetime: a destroyed entity keeps its component data and a new entity sees it, so spawn initializes every field and `newEntity` empties the arrays. Id recycling: ids are reused at once, with no version bits.
