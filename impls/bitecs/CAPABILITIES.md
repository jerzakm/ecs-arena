# Capabilities: bitecs

Library version: bitecs 0.4.0 (npm release, `latest`)

Each row names a need of the game. The `Support` column says how bitecs meets it, and the `Code` column links the code that uses the library API. The three `Support` values are `native` (the API does the job as its docs teach), `emulated` (built from other features or a manual pass) and `absent` (the library has no way, so the implementation does something else). A note on a `native` row means a workaround from [Notes](#notes) is part of it. Every link points at the line that holds the named symbol, and `pnpm check:caps` checks that the line exists. The bitecs behaviors that the code works around are in [workarounds.ts L1](src/rts/workarounds.ts#L1).

## Notes

- **Spatial index.** The kernel owns the grid. bitecs keeps it current with calls: `add` at spawn ([entities.ts L74](src/rts/entities.ts#L74)), `update` for each unit that `move` sets ([systems/move.ts L58](src/rts/systems/move.ts#L58)), `remove` and `add` when a unit enters or leaves a garrison ([garrison.ts L9](src/rts/garrison.ts#L9), [garrison.ts L17](src/rts/garrison.ts#L17)), and `remove` from the `onRemove(Unit)` observer, which also catches the minions that the cascade of `destroyEntity` removes ([context.ts L51](src/rts/context.ts#L51)). The `inGrid` array stops the observer from removing a garrisoned unit twice. The handle is the entity id, so `Team.value[handle]` replaces a map back from the handle.
- **Start-of-phase positions.** SoA stores are not double-buffered. The `Start` component copies `Position` in the `moveStart` step, which the runner calls right before `move` ([systems/move.ts L8](src/rts/systems/move.ts#L8)). The deep-dive report shows it as its own `move.start` line.
- **Why not relations.** bitecs 0.4 relations were the first version of this implementation, and `war` took 15 to 20 minutes for one seed. Measured on `battle` (400 ticks, one process): 11.8 s with relations and 1.9 s without. 57% of the first profile was `removeEntity`. A pair `Rel(target)` registers a component for each target entity that is ever used. Destroying a target registers a `Wildcard(target)` query, which scans every live entity once and then stays in the world. `removeEntity` loops over all registered queries, and `addComponent` and `removeComponent` loop over the generations of component masks, so each destroy costs more for every id that was ever a target. Subjects pay too. `addComponent` of a pair puts both the subject and the target in `ctx.entitiesWithRelations` (bitecs `dist/core/index.mjs` L913-L917), and `removeEntity` builds a fresh `query(world, [Wildcard(eid)])` for each such entity (L1006), which scans all live entities and stays in `ctx.queries`. `removeRelation` never prunes the set. So a unit with any native link costs a full scan when it dies. `getRelationTargets` also copies the component list of the entity on each call. The docs show relations for small graphs. This game has about 50k entities, a destroy burst of hundreds each tick and a link in nearly every unit. So every link is a plain SoA component that stores the target entity id, as the bitecs docs teach for data that is not a flag. The cost is that bitecs no longer clears the link when the target dies, so the game does it (workaround 1). `GarrisonOf` is the one link that could be native, since its fan-in is small and bounded by `garrisonCap`. It stays emulated because a pair would still put every shrine and every unit that ever garrisons into `entitiesWithRelations`, so each of their destroys would scan all entities, and the link would need a read path unlike the other five. This is argued from the bitecs source and not measured on `war`.
- **Workaround 1, clearing links by hand.** A destroyed entity cannot clear the plain stores that name it, and bitecs recycles ids at once. `destroyEntity` is the one destroy function ([entities.ts L44](src/rts/entities.ts#L44)): it destroys the minions of the entity, removes the entity from the reverse lists of its own links, destroys the items it holds, and records a destroyed unit in `ctx.destroyed`. `sweepDestroyed` ([workarounds.ts sweepDestroyed L15](src/rts/workarounds.ts#L15)) then walks `query(world, Q.identified)` once and clears `Targets`, `LastHitBy` and `FiredBy` that name a destroyed unit and the threats from it. It runs inside `cleanup` ([systems/cleanup.ts L83](src/rts/systems/cleanup.ts#L83)), before the projectile check reads `Targets.to` and before any spawn can reuse an id. Nothing else destroys units. Inside the destroy loop a link can name an entity that was just removed, so the kill credit checks `entityExists`.
- **Workaround 2, reverse lists.** `MemberOf`, `ChildOf` and `GarrisonOf` keep `from[target]`, an array of subjects, because three reads need "who points at X": promotion of members, the minion cascade and count, and the garrison of a shrine ([relations.ts L8](src/rts/relations.ts#L8)). `setLink` and `clearLink` keep it in step. The lists are short (members, minions, at most `garrisonCap`). `Targets` has no list, since its fan-in is large and only the sweep reads it. The stores are module-level, so `createContext` and `load` empty the lists with `resetStores`.
- **Workaround 3, items die with the unit.** `Equips` is a pair of arrays in the unit, and `destroyEntity` removes each item entity of a destroyed unit ([entities.ts L56](src/rts/entities.ts#L56)).
- **Workaround 4, hierarchy order.** `Hierarchy(relation)` in a query orders entities by depth, but it needs a bitecs relation, and it registers one query for each parent entity to track depth. The game has two links (`MemberOf` and `ChildOf`) and thousands of parents, so `move` computes the depth through the `to` arrays, memoized for the phase, and buckets the movers by depth ([systems/move.ts L12](src/rts/systems/move.ts#L12)).
- **Query cost.** The world holds a fixed set of queries, one for each term list in [queries.ts L9](src/rts/queries.ts#L9). Each `query` call hashes its terms, so a term list is a constant built once, and no system builds a query for each entity. The hot loops read typed arrays and never call `getRelationTargets`.
- **Per-entity arrays.** `Equips`, `Threat` and the reverse lists are plain arrays that are indexed by the entity id, and they are created for the entities that need them. A recycled slot is emptied by `newEntity` ([entities.ts newEntity L25](src/rts/entities.ts#L25)), and a store is never cleared otherwise, so each write sets the whole value.
- **Component stores are module-level.** One process can hold two sims one after the other, and a store keeps the data of the first. Every spawn writes every field, and `load` rewrites them from the save.
- **Entity id capacity.** The stores hold `CAP = 131072` ids, and `newEntity` throws above it ([entities.ts L27](src/rts/entities.ts#L27)). A typed array drops a write above its length without an error. The peak of `war` is about 50k entities.
- **Live query results.** `query` returns the live list of the query, and a removal is applied at the next committing `query`. No loop adds, removes or destroys while it reads a query result. Where a loop must change entities, it collects them first or copies the result with `Array.from`.
- **Recycled ids in the observer lists.** The lists that the `Added` observers fill can hold an entity that was destroyed before the phase read the list, and bitecs may have reused its id. `stillTagged` ([workarounds.ts stillTagged L33](src/rts/workarounds.ts#L33)) checks `entityExists` and the tag again before a phase uses the list.
- **`addComponent` and `removeComponent` need no guard.** Both return at once when nothing changes in 0.4.0, so no code asks `hasComponent` first ([components.ts hasComponent L4](src/rts/components.ts#L4)).
- **Four questions from the guide.** Exclusive swap: `setLink` overwrites `to[subject]` and moves the subject between reverse lists. Cleanup on destroy: `destroyEntity` and `sweepDestroyed` clear what names the entity (workaround 1). Store lifetime: a destroyed entity keeps its component data and a new entity sees it, so spawn initializes every field and `newEntity` empties the arrays. Id recycling: ids are reused at once, with no version bits.

## Survivors

Code: [src/survivors/](src/survivors/index.ts) and [src/shared/](src/shared/util.ts). Storage model: sparse. Each component is a module-level SoA of typed arrays indexed by the native entity id, each query keeps a sparse set of the matching entities, and there are no archetypes.

| Projectile `target` and `owner` | Plain gameId stores. The snapshot turns a link to a missing entity into -1 |
| Spatial index | The kernel grid, `add` at spawn, `update` in `grid.update`, `remove` from the `onRemove(Mob)` observer |
| World values, events | The custom world context holds the tick ([survivors/context.ts L10](src/survivors/context.ts#L10)). The totals, the event lists, the pending hits and the loadout cache are plain per-world data ([survivors/context.ts L12](src/survivors/context.ts#L12)) |
| Save and load | Emulated like the RTS save. `save` reads each entity kind through its query ([survivors/save.ts L29](src/survivors/save.ts#L29)). `load` empties the world with `resetWorld`, registers the observers again and spawns every entity in gameId order, then relinks `SummonedBy` ([survivors/save.ts L66](src/survivors/save.ts#L66)) |
| Order | A query result has no gameId order, so a rule that depends on order sorts a copy by `GameId`. A rule that is a sum or a set reads the live result |

## Factory

Code: [src/factory/](src/factory/index.ts) and [src/shared/](src/shared/util.ts). Storage model: sparse. Each component is a module-level SoA of typed arrays indexed by the native entity id, each query keeps a sparse set of the matching entities, and there are no archetypes.

| Facet | bitecs features used |
|---|---|
| Query over a small active set in a large world (`work.query`) | `Working` is a tag component ([factory/components.ts Working L13](src/factory/components.ts#L13)). `work` loops over `query(world, Q.workBoost)` and `query(world, Q.workPlain)`, so it touches only the Working machines, 2,000 of 150,000 in `works` ([factory/systems/machines.ts L21](src/factory/systems/machines.ts#L21), [factory/systems/machines.ts L22](src/factory/systems/machines.ts#L22)). Native |
| Change detection at scale (`state.changed`) | Emulated. bitecs 0.4 has no per-tick change query for plain stores, so a `dirty` list of machine entities is built every tick by `work`, `dock` and `power` ([factory/entities.ts markDirty L35](src/factory/entities.ts#L35)). `state` re-checks the dirty list and diffs the Working set and the dirty list against the `p*` columns into the `changed` list ([factory/systems/machines.ts note L35](src/factory/systems/machines.ts#L35), [factory/systems/machines.ts L60](src/factory/systems/machines.ts#L60)). The snapshot sorts the list ([factory/snapshot.ts changed L18](src/factory/snapshot.ts#L18)) |
| Bulk tag change on a large set (`power.toggle`) | `removeComponent` and `addComponent` of the `Powered` tag for each machine of a district that changes ([factory/systems/power.ts removeComponent L18](src/factory/systems/power.ts#L18), [factory/systems/power.ts addComponent L19](src/factory/systems/power.ts#L19)). A `Manual` machine is skipped with `hasComponent` ([factory/systems/power.ts L17](src/factory/systems/power.ts#L17)). There is no bulk form of the call, so about 700 calls run in the tick of an outage |
| One-to-many lookup (district to machines) | Emulated. `ctx.districts` is a plain list of machine entities for each district ([factory/context.ts L10](src/factory/context.ts#L10)). The machine id lookup `ctx.machines` is a plain list too. A district is not an entity, so a relation has no target to name |
| `Or` query (`Powered` or `Manual`) | `Or(Powered, Manual)` in the `live` query, which the full re-check at tick 0 walks ([factory/queries.ts Or L8](src/factory/queries.ts#L8), [factory/systems/machines.ts Q.live L60](src/factory/systems/machines.ts#L60)). The per-machine test in the later ticks is two `hasComponent` calls ([factory/systems/machines.ts shouldWork L27](src/factory/systems/machines.ts#L27)), because bitecs 0.4 does not export a call that tests one entity against a query. Native for the query, emulated for the test |
| Optional component (`boost`) | `Boost` is added only to the machines that have it ([factory/entities.ts Boost L27](src/factory/entities.ts#L27)). `work` splits the Working set with `[Working, Boost]` and `[Working, Not(Boost)]`, so no loop tests for the component ([factory/queries.ts workBoost L11](src/factory/queries.ts#L11), [factory/queries.ts workPlain L12](src/factory/queries.ts#L12)). The flag bit in the snapshot is `hasComponent(Boost)` ([factory/entities.ts flagsOf L42](src/factory/entities.ts#L42)). Native |
| Dense iteration over wide components (`drone.move`) | `Transform` and `Motion` are typed arrays, and `steer` and `move` loop over `query(world, Q.drones)` with indexed reads and writes ([factory/components.ts Transform L18](src/factory/components.ts#L18), [factory/systems/drone.ts L24](src/factory/systems/drone.ts#L24)). The crates read the same `Transform` store. Native |
| Transform propagation (`transform`) | Emulated. `Crate.parent` is the parent entity, a drone or a crate ([factory/components.ts Crate L23](src/factory/components.ts#L23)), and a depth tag is set at spawn ([factory/components.ts DEPTH_TAGS L29](src/factory/components.ts#L29)). `transform` visits one depth query at a time, so a crate reads a parent that the same pass wrote ([factory/systems/transform.ts L11](src/factory/systems/transform.ts#L11)). See "Why not relations" |
| Bulk and deferred structural change (`churn`) | A crate is an entity from `addEntity` with `addComponents` ([factory/entities.ts addCrate L65](src/factory/entities.ts#L65)). `dock` collects the destroys in `ctx.doomed` and `flush` removes them at the end of the phase ([factory/entities.ts flush L92](src/factory/entities.ts#L92), [factory/systems/dock.ts destroy L43](src/factory/systems/dock.ts#L43)). A shift retires a drone with its crates and spawns new drones in one batch ([factory/entities.ts destroyDrone L85](src/factory/entities.ts#L85), [factory/systems/shift.ts L26](src/factory/systems/shift.ts#L26)). Native, except that the crate chain is destroyed by the code |
| Bulk create (`build`) | `makeMachine` with `addEntity` and `addComponents` for each of the 150,000 machines ([factory/entities.ts addComponents L17](src/factory/entities.ts#L17), [factory/systems/build.ts L8](src/factory/systems/build.ts#L8)). The entity capacity is a store size: `CAP` and `GameId` hold 262,144 entities ([factory/components.ts CAP L3](src/factory/components.ts#L3)) |
| Drone links | `Drone.source`, `Drone.sink` and `Drone.top` are plain entity stores ([factory/components.ts Drone L21](src/factory/components.ts#L21)). A machine is never destroyed. A crate that is destroyed is no longer the `top` of any drone |
| Why not relations | The first version had `ChildOf`, exclusive with `autoRemoveSubject`, and read the order from `Cascade(ChildOf)`. It was correct (the traces matched) and slow: `dock` took 4,291 ms for 400 ticks of a 20,000-machine world, 34 ms with the plain store (rough, on a loaded machine). The cause is the one in the RTS section: each crate that is a target registers a pair component and a `Wildcard` query, and `removeEntity` scans them. `Cascade` also keeps a depth cache that `removeEntity` does not clear, so a recycled id carries the depth of its last owner. The `works` verify did not finish in 15 minutes |
| World values | The custom world context holds the tick ([factory/context.ts L6](src/factory/context.ts#L6)). The totals, the district power flags and the lists are plain per-world data |
| Save and load | Emulated. `save` copies the four machine columns (`input`, `output`, `progress`, `flags`) into typed arrays and reads drones and crates through their queries ([factory/save.ts L36](src/factory/save.ts#L36)). `load` keeps the machine entities and writes the columns back with `addComponent` and `removeComponent` for `Powered` and `Working` ([factory/save.ts setTag L69](src/factory/save.ts#L69)), resets all change tracking, removes every drone and crate and spawns them again in gameId order ([factory/save.ts L54](src/factory/save.ts#L54)) |
| Order | A query result has no gameId order, so `dock`, `shift` and the snapshot sort a copy by `GameId` ([factory/systems/dock.ts byGameId L21](src/factory/systems/dock.ts#L21), [factory/snapshot.ts L18](src/factory/snapshot.ts#L18)). `dock` sorts only the drones in reach, because reach depends on positions that the phase does not write. `work`, `steer` and `move` read the live result |
