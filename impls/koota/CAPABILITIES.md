## Notes

- **Spatial index.** The kernel owns the grid (`SpatialGrid` in `packages/spec/src/grid.ts`). koota keeps it current with three calls: `add` at spawn ([spawning.ts L20](src/spawning.ts#L20)), `update` for each unit that `move` sets ([move.ts L50](src/systems/move.ts#L50)), and `remove` from an `onRemove(Unit)` observer, which also catches the minions that `ChildOf` destroys ([context.ts L40](src/context.ts#L40)). The handle is the entity id. `unitAt` and `teamAt` map a handle back to the entity and its team ([context.ts L14](src/context.ts#L14)).
- **Start-of-phase positions.** koota has no double-buffered stores. The `Start` trait copies `Position` at the top of `move` ([move.ts L11](src/systems/move.ts#L11)). This costs one extra pass.
- **Hierarchy order.** `move` computes the depth of each unit by walking `MemberOf` and `ChildOf` ([move.ts L15](src/systems/move.ts#L15)), memoizes it for the phase, buckets the units by depth with one `readEach`, and moves them with `get` and `set` on each entity ([move.ts L29](src/systems/move.ts#L29)). A query cannot filter by depth, so this pass does not use `updateEach`.
- **Intents.** Damage, heal and buff intents are plain per-phase accumulators in `combat`, resolved in the same phase. Nothing is added to or removed from entities to carry them.
- **Per-unit relation queries.** `promote` runs `world.query(MemberOf(unit))` for each dead or leaving unit ([cleanup.ts L10](src/systems/cleanup.ts#L10)). The minion count in `spawn` does the same with `ChildOf` ([spawn.ts L38](src/systems/spawn.ts#L38)). koota 0.6.6 answers a query for one relation with an entity target from the relation index and caches no query, so this is cheap. The flee step scans `MemberOf('*')` once ([morale.ts L33](src/systems/morale.ts#L33)) because it needs the members of all routed leaders.
- **Trackers need `Unit`.** In 0.6.6 a query that holds only a tracker modifier reports every new entity as added, so each tracker query also holds `Unit` ([queries.ts L10](src/queries.ts#L10)).
- **`Or` over trackers.** `Or(Added(T), Removed(T))` together with another trait did not report a trait that was added after spawn. The dirty-stats set uses observers instead ([derived-stats.ts L28](src/derived-stats.ts#L28)).
- **`Added` on a relation.** It fires for the first pair of an entity only. A second `Equips` pair raises no `Added(Equips)`, which is why stats use `onAdd(Equips, ...)`. Observers fire for every pair.
- **`set` with an updater on a relation pair.** `entity.set(Threat(a), (t) => ...)` is ignored in 0.6.6. The code reads the amount first and passes an object ([combat.ts L136](src/systems/combat.ts#L136)).
- **Collected entity lists.** Structural changes (add, remove, destroy) never run inside a `readEach` or `updateEach` loop. The code collects entities first and changes them after the loop. Where a loop makes no structural change, it iterates the query result directly.
- **Observers on destroyed units.** `onRemove` fires for a destroyed unit, so the stats phase skips a dirty entity that is no longer alive ([stats.ts L35](src/systems/stats.ts#L35)).
