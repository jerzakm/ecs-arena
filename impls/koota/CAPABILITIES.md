## Notes

- **Spatial index.** The kernel owns the grid (`SpatialGrid` in `packages/spec/src/grid.ts`). koota keeps it current with calls: `add` at spawn ([entities.ts L36](src/rts/entities.ts#L36)), `update` for each unit that `move` sets ([systems/move.ts L58](src/rts/systems/move.ts#L58)), `remove` and `add` when a unit enters or leaves a garrison ([garrison.ts L10](src/rts/garrison.ts#L10), [garrison.ts L17](src/rts/garrison.ts#L17)), and `remove` from an `onRemove(Unit)` observer, which also catches the minions that `ChildOf` destroys. The `inGrid` array stops the observer from removing a garrisoned unit twice ([context.ts L30](src/rts/context.ts#L30)). The handle is the entity id. `unitAt` and `teamAt` map a handle back to the entity and its team ([context.ts L14](src/rts/context.ts#L14)).
- **Start-of-phase positions.** koota has no double-buffered stores. The `Start` trait copies `Position` in the `moveStart` step, which the runner calls right before `move` ([systems/move.ts L6](src/rts/systems/move.ts#L6)). This costs one extra pass, and the deep-dive report shows it as its own `move.start` line.
- **Hierarchy order.** `move` computes the depth of each unit by walking `MemberOf` and `ChildOf` ([systems/move.ts L17](src/rts/systems/move.ts#L17)), memoizes it for the phase, buckets the units by depth with one `readEach`, and moves them with `get` and `set` on each entity ([systems/move.ts L31](src/rts/systems/move.ts#L31)). A query cannot filter by depth, so this pass does not use `updateEach`.
- **Intents.** Damage, heal and buff intents are plain per-phase accumulators in `combat`, resolved in the same phase. Nothing is added to or removed from entities to carry them.
- **Per-unit relation queries.** `promote` runs `world.query(MemberOf(unit))` for each dead or leaving unit ([systems/cleanup.ts L10](src/rts/systems/cleanup.ts#L10)). The minion count in `spawn` does the same with `ChildOf` ([systems/spawn.ts ChildOf L40](src/rts/systems/spawn.ts#L40)). koota 0.6.6 answers a query for one relation with an entity target from the relation index and caches no query, so this is cheap. The flee step scans `MemberOf('*')` once ([systems/morale.ts L33](src/rts/systems/morale.ts#L33)) because it needs the members of all routed leaders.
- **Trackers need an anchor trait.** In 0.6.6 a query that holds only a tracker modifier reports every new entity as added, so each tracker query also holds `Unit` ([workarounds.ts L9](src/shared/workarounds.ts#L9)).
- **`Or` over trackers.** `Or(Added(T), Removed(T))` together with another trait did not report a trait that was added after spawn. The dirty-stats set uses observers instead ([derived-stats.ts L27](src/rts/derived-stats.ts#L27)).
- **`Added` on a relation.** It fires for the first pair of an entity only. A second `Equips` pair raises no `Added(Equips)`, which is why stats use observers on every pair ([workarounds.ts L15](src/shared/workarounds.ts#L15)).
- **`set` with an updater on a relation pair.** `entity.set(Threat(a), (t) => ...)` is ignored in 0.6.6. The code reads the amount first and passes an object ([systems/combat.ts L20](src/rts/systems/combat.ts#L20)).
- **Collected entity lists.** Structural changes (add, remove, destroy) never run inside a `readEach` or `updateEach` loop. The code collects entities first and changes them after the loop. Where a loop makes no structural change, it iterates the query result directly.
- **Observers on destroyed units.** `onRemove` fires for a destroyed unit, so the stats phase skips a dirty entity that is no longer alive ([systems/stats.ts L38](src/rts/systems/stats.ts#L38)).

## Survivors

Storage model: archetype. Every facet is plain koota: entities, trait tags, queries with `Not`, relations, trackers and observers. No typed arrays and no hand-made component store, and no cast around a koota type. The cost shows in the facets that favor a sparse set (tag add and remove, trait tags, affixes), where each change moves a row. The code is in [`src/survivors/`](src/survivors/). The singletons are the world traits `Clock`, `Totals` and `Loadout` ([survivors/traits.ts L103](src/survivors/traits.ts#L103)). The 36 systems are in `systems/`, wired by the `SYSTEMS` table of the spec in [survivors/index.ts L18](src/survivors/index.ts#L18).

Notes for survivors:

- **`updateEach` and `Changed`.** In 0.6.6 a write in `updateEach` does not flag `Changed` with the default `'auto'` change detection, so a tracker query reads nothing. `move.mobs` passes `FLAG_CHANGED` ([workarounds.ts FLAG_CHANGED L24](src/shared/workarounds.ts#L24)). A tracker query can also return an entity without the other tags on its first read, so `grid.update` checks the `Mob` tag ([survivors/systems/move.ts Mob L53](src/survivors/systems/move.ts#L53)).
- **Structural changes.** As in the RTS code, no add, remove or destroy runs inside a `readEach` or `updateEach`. A system collects entities first.
- **Query order.** A query result has no order. A system that creates entities, or whose result depends on the order, sorts its small candidate list by `gameId` first.

## Factory

Storage model: archetype. Machines, drones and crates are koota entities. `Working`, `Powered` and `Manual` are tags, `Boost` is a trait that one machine in eight has, drone and machine fields are SoA traits, and a crate is a `ChildOf` child of its drone or of the crate below it. District power is the `Lit` tag on a district entity, and a machine reaches its district through the `InDistrict` relation. The code is in [`src/factory/`](src/factory/). The singleton is the world trait `Totals` ([factory/traits.ts Totals L43](src/factory/traits.ts#L43)).

Notes for factory:

- **Lookup by gameId is emulated.** koota has no lookup by a user key, so `ctx.machines` is an array from `gameId - 1` to the machine entity, filled at build ([factory/entities.ts L18](src/factory/entities.ts#L18)).
- **A tracker modifier puts its trait first in the result tuple.** `Changed(Io)` returns `Io` in the first slot, so the `ioAble` query lists only `Kind` after it ([factory/queries.ts L6](src/factory/queries.ts#L6)).
- **Each tracker has its own modifier.** One `createChanged()` instance shared by two queries lets the first read reset the second, so each tracker query calls it again.
- **Dock sorts a small list.** One query finds the drones in reach of their goal, and only that list is sorted by gameId, because each drone sees the machine values that the drones before it wrote ([factory/systems/dock.ts L18](src/factory/systems/dock.ts#L18)).
