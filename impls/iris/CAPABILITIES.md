# Capabilities: iris

Library version: iris-ecs 0.0.14 (npm release, https://github.com/r04423/iris)

Each row names a need of the game. `Support` is native (the documented API does the job), emulated (built from other features or a manual pass) or absent. Links point into the files under [`src/`](src/).

**Relations versus plain link fields.** iris stores a relation pair as a component id, so every distinct target is its own component id, and an entity that holds the pair lands in an archetype of its own for that target. With B archetypes among the entities that hold a link and T distinct targets, one relation makes up to B x T archetypes, and `Wildcard` aggregates add more. Every query walks the archetypes it matches, and iris tests each new archetype against every cached query. T is small for `ChildOf` (the summoners) and `GarrisonOf` (7 shrines). T is nearly the unit count for `Targets`, `LastHitBy`, `FiredBy` and `MemberOf`: each unit names a different entity and changes it every tick. The first version used relations for all of them, and at tick 300 of `skirmish` that made 13,932 archetypes for about 800 live units (see Notes for the profile and the timings). So those four links are `u32` fields of ordinary components, and `Threat` and `Equips` are many-to-many lists in a `Type.ref<number[]>()` field. A field holds a gameId and never a native entity id (see Notes, Id reuse). `ChildOf` and `GarrisonOf` are native relations. `GarrisonOf` replaces an earlier `Garrisoned` field: it measured the same in time, and it removes the scans over every garrisoned unit (see the Garrison row).

## Notes

- **Why the links are fields (measured).** `skirmish`, seed 1, first 600 ticks, `node --cpu-prof`: koota 8.4 s. iris with relation pairs for every link: 17.3 s for the first 300 ticks alone, with 13,932 archetypes at tick 300, 21% of the time in `queryEntitiesWithMeta` (walking archetypes) and another 5.6% in `getRelationTargets`. iris with link fields: 8.7 s for 600 ticks, 1,048 archetypes at tick 300. The remaining archetypes come from tag and buff combinations, which is the fragmentation the iris benchmarks use as their normal case. `GarrisonOf` as a relation (T = 7): `skirmish-smoke` peaks at 1,430 archetypes against 1,322 with a `Garrisoned` field, and `battle-smoke` peaks at 3,884 against 3,664, and both are equal at tick 300 before any shrine holds a garrison. The `battle-smoke` time with the relation is within 3% of the field version, in either direction, over interleaved runs.
- **Id reuse (verified in the iris source).** An entity id has an 8-bit generation (`extractMeta(entityId) + 1 & 255`) and `freeIds` is a stack, so a slot that is destroyed and created again 256 times gives the same id as a stale reference, and `isEntityAlive` reports it as live. So no field or list holds a native entity id across a tick. A link holds a gameId, which `NextId` never issues twice, and `ctx.entityOf` (kept by the `componentAdded` and `entityDestroying` observers) resolves it. The first version cleared nothing and checked `isEntityAlive`, which is correct only until a slot wraps. The other fix is a reverse index of inbound links, cleaned in the destroy observer. It needs every link write and every list edit to maintain it, and a gameId needs none of that, so it is not used. Ids kept inside one phase (the `dirty` set, the per-phase maps) cannot wrap: no entity is created between their write and their read.
- **Load reproduces the live state, so order must not matter.** `load` creates the entities in gameId order, so archetype and row order differ from a live run. Each loop over a query result is order-independent (counts, flags, per-entity updates: the `Overwhelmed` fan-in in combat, the banner and alive scans in stats, effects, morale) or sorted by gameId before it matters (the `leaving` list and the ground items in cleanup, `shots` and `damages` in combat, the summoners in spawn, the render rows). The replay hashes of every golden, across the load every 200 ticks, check it.
- **The scheduler is async, so a driver runs the systems.** iris runs systems through `runOnce` or `run`, and both are async: the frame awaits every schedule, so it cannot finish before the caller yields. The sim contract is synchronous, and the harness calls the phases one by one, so the scheduler cannot own the frame. `added()`, `changed()` and `readEvents` only work while `world.execution.systemId` is set, so the code cannot call the systems directly either. `driver.ts` does what one scheduler slot does for a sync system: it sets the system id through `getWorldInternals`, calls `system.tick(world)` and clears the id ([driver.ts L10](src/shared/driver.ts#L10)). It also repeats the end-of-frame `flushEvents` ([driver.ts flushEvents L23](src/shared/driver.ts#L23)), which the `stats` phase calls ([index.ts L33](src/rts/index.ts#L33)). Without the flush, the removal events that iris emits for every component of every destroyed entity would grow without bound. The package pins iris-ecs 0.0.14 exactly, because the driver reads internals. The systems stay ordinary `defineSystem` systems, and schedules, sets and conditions are not used. A caller that can await would use `addSystem` and `runOnce` instead. The driver is under 4% of the profile, so it is not a cause of the slowness.
- **Experimental column API (`EXPERIMENTAL_queryColumns`).** iris documents it as the hot-loop API: the callback gets each matching archetype's entity array and one column object per data-bearing term. It may change or go away, so only measured hot loops use it, and the version is pinned. Rules that the code follows: no structural change (add, remove, create, destroy) inside a callback, no retained column or entity array, and `markComponentChanged` after a direct column write to a component that a `changed()` tracker reads. No component that a column write changes (`Position`, `Start`, `Cooldown`) has a tracker today (`KillCount`, the only one, is written through `setComponentValue`). It rejects `added()` and `changed()` terms, so the tracker passes stay on `collectEntities`. Conclusions (interleaved runs, minimum of 3, `battle-smoke`): a column pass pays for a hot loop that reads several fields. The kept passes cut 3 to 10% each: the `Start` copy, the mover read and write passes (split into three query groups, so only a member or a minion looks up a parent), the banner scan (`MemberOf` as a column, three groups), the render pass (tags read once for each archetype, rows in a typed buffer with a packed-key sort), the target pass, and the fan-in, attack and cooldown passes. Together they ran `battle-smoke` about 30% faster. The projectile step gains 0.4%, so it stays a `collectEntities` loop. A save that checks tags once for each archetype cuts the save phase by 27% but the whole run by 1.5%, so it was not kept. Reading the `Targets` link from the columns in the target and attack passes, and the `Targets` and `MemberOf` link and offsets in the move read pass, cut `skirmish-smoke`, `battle-smoke` and `war-smoke` by 5.5%, 8.4% and 8.1%. Dropping the `changed(KillCount)` tracker for the observer cut them by 5.2%, 6.9% and 6.8%. Compare percentages across runs, not seconds.
- **Kernel grid.** The kernel owns the grid (`SpatialGrid`). The handle is a dense int that `HandleGrid` hands out for each unit ([handle-grid.ts L19](src/shared/handle-grid.ts#L19)), mapped back to the entity by `entityAt`. A native entity id is not dense (it holds a type, a generation and a slot), so it cannot be the handle. The grid is kept current with `add` at spawn, `update` for each unit that `move` sets ([move.ts L111](src/rts/systems/move.ts#L111)), `remove` and `add` when a unit enters or leaves a garrison ([garrison.ts L7](src/rts/garrison.ts#L7), [garrison.ts L15](src/rts/garrison.ts#L15)), and `remove` from an `entityDestroying` observer, which also catches the minions that `ChildOf` destroys ([context.ts L36](src/rts/context.ts#L36)). The `inGrid` array stops the observer from removing a garrisoned unit twice.
- **Start-of-phase positions.** iris has no double-buffered stores. The `Start` component copies `Position` in the `moveStart` step, which the runner calls right before `move` ([move.ts move L16](src/rts/systems/move.ts#L16)). This costs one extra pass, now a column loop, and the deep-dive report shows it as its own `move.start` line.
- **Hierarchy order.** `move` computes the depth of each unit by walking `MemberOf` and `ChildOf` ([move.ts L33](src/rts/systems/move.ts#L33)), memoizes it for the phase, buckets the units by depth in three column passes (units with `MemberOf`, minions, the rest), and writes the new positions back in three more, and moves them level by level. A query cannot filter by depth.
- **Intents.** Damage, heal and buff intents are plain per-phase accumulators in `combat`, resolved in the same phase. Nothing is added to or removed from entities to carry them.
- **No query per target entity.** The relation way to find the sources of a target, `collectEntities(world, [pair(ChildOf, unit)])`, makes iris cache one query for each target and test it against every new archetype. So the code scans once and groups by target: the members of a dying leader in `cleanup` ([cleanup.ts L25](src/rts/systems/cleanup.ts#L25)), the minions of each summoner in `spawn` ([spawn.ts L48](src/rts/systems/spawn.ts#L48)), and who targets a unit that enters a garrison ([objectives.ts L12](src/rts/systems/objectives.ts#L12)). The one per-target query that stays is `[pair(GarrisonOf, shrine)]`, for 7 shrines.
- **Link reads.** A link names a gameId, and the gameId can be dead. `targetOf` reads a dead target as no link, as a relation pair behaves, and `threatOf` hands the edges out for each reader to resolve.
- **Idempotent add.** `addComponent` of a component that is there changes nothing, not even the data. Where the value must change (the buff timers, the leader of a `MemberOf`), the code tests with `hasComponent` and writes with `setComponentValue` or `setComponent`.
- **Collected entity lists.** Structural changes (add, remove, destroy) never run inside a query callback. `collectEntities` returns a copy, so the loops change the world freely, and the code skips an entity that a cascade destroyed with `isEntityAlive`. That check is safe, because no entity is created in the same phase.
- **Observers on destroyed units.** `componentRemoved` does not fire for a destroyed entity, so the dirty set can hold a unit that is gone, and the stats phase skips it ([stats.ts L48](src/rts/systems/stats.ts#L48)).

## Survivors (game 2)

Storage model: archetype. Every mob, projectile, pickup, particle and held upgrade is an entity. Status tags and trait bits are components, so a tag add or remove moves a row between archetypes. The spatial grid, the five event lists, the hit batch and the loadout are plain per-world data in `Ctx`, as in the RTS impl. The entry is [survivors/index.ts](src/survivors/index.ts). It wires the 36 systems of the spec `SYSTEMS` table, one `defineSystem` for each, in the 11 phases.

| Facet | iris feature | Code |

## Factory

Storage model: archetype. Every machine, drone and crate is an entity. `Working`, `Powered` and `Manual` are tag components, so a power toggle or a `Working` change moves a row between archetypes. The totals are a resource, and the `up` flags of the districts, the machine list of each district and the `seen` values of the changed list are plain per-world data in `Ctx`. The entry is [factory/index.ts](src/factory/index.ts). It wires one `defineSystem` for each of the 9 phases. It reuses the version pin and the event flush of [driver.ts](src/shared/driver.ts).
